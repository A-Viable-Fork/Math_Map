# MM-DR-003 — Prior-art assessment of D9 and its Android binding

Research cutoff: **2026-10-11 (UTC)**. Subject: the supplied, generated Math_Map D9 design. Citations [R01]–[R39] resolve in Section 5.

## 1. Answer

**[RESULT — assessment] The broad four-part architecture is a RECOMBINATION of established work, and restricted implementations already combine all four parts.** Guardians is a particularly direct example: a registry pairs input/output descriptions with contracts and flow labels, binds tools to implementations, and verifies workflows against user-defined policies. CaMeLoT/CaMeL combine tool specifications, provenance/taint propagation, concrete tool adapters, and static plus runtime policy checks; TACIT combines typed operation interfaces, tracked authority, concrete filesystem/network/process implementations, and composition through capture checking. Older Frama-C/ACSL and Android FlowDroid/StubDroid cover substantial versions of the same architecture. **[SYSTEM]** These systems exist, but each has a restricted language, property family, or platform [R01–R06, R12–R13]. **[UNVERIFIED verdict; CLAIMED proposed capability]** I did not establish an existing, validated Android 16/Linux atlas covering D9's exact 19 contracts, including shared-epoch revocation, atomic audit, replay prevention, bounded erasure, and timed/probabilistic noninterference. That conjunction remains **UNVERIFIED**, not novel. The supplied files also do not demonstrate that conjunction: they contain specifications and candidate bindings, without an executable composition checker or binding-conformance proofs.

### Evidence and scope

- **RESULT** means a fact obtained by inspecting the supplied files or source, or an explicitly identified inference from that inspection. It does not mean that this review reproduced a published experiment.
- **SYSTEM** means an existing implementation, specification, or published construction is described by primary sources. Its existence is stronger evidence than an independently untested security guarantee.
- **CLAIMED** identifies a security, coverage, or performance assertion that this review did not prove or reproduce.
- **FOLKLORE** identifies a commonly repeated assertion without adequate support. Such assertions are rejected below, not used as evidence.
- **UNVERIFIED** is a verdict or coverage status, separate from those four evidence labels.

**[RESULT]** I inspected the attached prompt and four JSON files, project documentation, selected implementation files, paper text, licenses, and release/commit metadata. I did not execute the research systems, reproduce their benchmarks, prove D9 contracts, or independently re-audit every AOSP file cited by the supplied Android bindings. Search covered Android analysis, formal specification and abstract interpretation, agent IFC/capabilities, policy languages, typed effects, provenance systems, and capability OS architectures. It is an overlap assessment, not an exhaustive proof of absence.

**[SYSTEM]** Commit dates below are the latest commits observed on the named branch at or before the cutoff, using the commit's committer timestamp. They are not repository “updated” times, and a documentation commit does not establish supported platform coverage. Where an official release is available, it is distinguished from a commit. Unknown dates or rights are stated explicitly.

## 3. The three closest matches

### 3.1 Guardians: the closest explicit registry-and-contract design

**[SYSTEM]** Meijer's published architecture separates workflow generation, verification and execution [R01]. The public implementation by **Nada Amin and contributors** has a ToolSpec containing parameter descriptions, return type, preconditions, postconditions, frame conditions, and source/sink labels. A registry pairs each specification with a Python callable. Policy objects hold allowed tools, automata, taint rules and invariants. Those two inspected source files make the overlap concrete; it is more than a conceptual resemblance.

**[SYSTEM]** Its design document describes symbolic data references, taint propagation, sequencing policies and Z3 verification before tools run. **[CLAIMED]** Security correctness and test-count claims were not independently reproduced. **[RESULT]** A string “type” and an Any default are weaker than a sound static type system; declarations are assumptions about tool implementations unless separately validated.

| Comparison | Assessment |
|---|---|
| What it provides that the supplied D9 package does not | **[RESULT]** Executable registry, workflow representation, verification machinery, policy structures and execution path; source is available. D9 supplies contracts and bindings but no checker. |
| What D9 specifies that it does not establish | **[RESULT — inference]** A platform-neutral 27-operation catalogue; explicit carriers for current state versus historical traces; the full 19-contract conjunction and 51 Android 16 candidate rows. No inspected Guardians evidence establishes this scope. |
| Presentational differences | **[RESULT — inference]** Calling the registry an atlas, assigning invariant IDs, and displaying losses join by join can be different views of contracts and propagated analysis. These are not sufficient novelty grounds. |
| Substantive differences | **[RESULT — inference]** Proving each Android adapter, shared-epoch revocation, atomic audit, bounded erasure and timed/probabilistic properties would add real capabilities. They remain proposed in D9. |

**[RESULT — assessment]** Guards must execute before committed effects. A runtime postcondition checked after an irreversible tool action can detect a violation but cannot supply D9's “rejection has no external effect” premise. Frame conditions also require a semantics for actual state and old values; the presence of a frame-condition field is not a proof that the full frame logic is implemented. Latest inspected snapshot: main **59e52d9**, **2026-07-16**, Python 3.11+.

### 3.2 TACIT: the closest typed capability-and-operation harness

**[SYSTEM]** TACIT's inspected interface exposes scoped filesystem, network and process capabilities; handles retain their originating capability, and parameter checks constrain paths/hosts/commands. Classified values have restricted map/flatMap operations accepting pure computations. Scala capture checking constrains which capabilities an agent-generated program can retain and use [R03]. The trusted interface includes explicit safety assumptions; the host implementation remains part of the trusted computing base.

**[CLAIMED]** The paper reports that agents can generate usable capability-safe code and that the harness prevents the modeled unsafe behaviors. These experiments were not rerun. **[RESULT]** Its concrete typed interfaces are stronger implementation evidence than D9's descriptive carrier lists. Conversely, a classified-data network operation authorized for a host is not an unconditional promise that no data leaves the device.

| Comparison | Assessment |
|---|---|
| What it provides that the supplied D9 package does not | **[RESULT]** A compiler-backed capture discipline, sealed/scoped capability interfaces, concrete host operations and executable agent experiments. |
| What D9 specifies that it does not establish | **[RESULT — inference]** Historical authenticated origin sets distinct from endorsement, a generic invariant-relation vocabulary, revocation/audit/freshness/erasure contracts, and Android-specific deviation records. |
| Presentational differences | **[RESULT — inference]** Capability/effect interfaces can be rendered as operation atlas entries. Renaming or tabulating them is presentation. |
| Substantive differences | **[RESULT — inference]** A faithful Android implementation and a checker joining state, history and relational guarantees would be additional functionality. Compiler capability confinement alone does not supply those guarantees. |

**[RESULT — assessment]** Local purity is valuable prior art for EBND and classified-data confinement. It must not be equated with full timed/resource/termination-sensitive noninterference or authenticated complete origin history. TACIT's protection of confidentiality also does not automatically establish integrity of trusted decisions. Latest inspected snapshot: main **476b421**, **2026-08-17**, experimental Scala 3/JDK 17+.

### 3.3 CaMeLoT with CaMeL: the closest policy-over-composition design

**[SYSTEM]** CaMeLoT translates a restricted Python plan into a finite state model, records tool calls and argument-level provenance/taint, and checks temporal rules with nuXmv [R02]. Its repository provides tool-signature tables, policy suites, a translation pipeline, counterexample feedback and a repair loop. CaMeL supplies the restricted interpreter, concrete tools, value-capability tracking and runtime policy checks [R04]. These are two layers of an existing system, not a new atlas invented by D9.

**[SYSTEM]** Policy examples constrain which origins may supply particular tool arguments and the order/history of actions; the paper also describes liveness checks. **[RESULT]** Plain CTL is not a general logic for D9's relational or probabilistic noninterference properties; those require another encoding/analysis [R36]. Actual reader permissions and concrete values can still need runtime checking.

| Comparison | Assessment |
|---|---|
| What it provides that the supplied D9 package does not | **[RESULT]** An executable plan-to-model translation, temporal policy checking, counterexamples and repair, plus a runtime enforcement layer. |
| What D9 specifies that it does not establish | **[RESULT — inference]** A broader multi-carrier vocabulary; exact-bound signature descriptors; fresh approval histories; revocation linearization; complete audit; erasure inventories; Android API conformance. |
| Presentational differences | **[RESULT — inference]** Recasting tool transfer functions and temporal predicates as atlas entries/invariant profiles largely reorganizes existing semantics. |
| Substantive differences | **[RESULT — inference]** A proved abstraction of all relevant Android side effects, concurrency and hyperproperties would expand the modeled capability. D9 does not yet provide that proof or executable expansion. |

**[RESULT]** The extension README explicitly describes configurable outcomes after failed repair: reject, warn and execute, or request guidance. A security deployment must select and validate rejection/enforcement behavior; the existence of a verification module is not enough. **[CLAIMED]** Benchmark results and completeness of the model translation were not reproduced here. Latest inspected CaMeLoT snapshot: main **f70e280**, **2026-09-03**; CaMeL: main **f083b6b**, **2025-06-20**.

**[RESULT — Q3 verdict]** None of these comparisons establishes an implemented D9 advantage. D9's breadth is a **specification difference**, and its normalized atlas/deviation presentation is chiefly an **organizational difference**. An advantage becomes substantive only when the additional contract is enforceable and its binding/composition is justified.

### Known limitations and failures the design should not repeat

1. **[SYSTEM → RESULT recommendation] Permission-map drift and incomplete paths.** Axplorer explicitly documents AppOps and native-code gaps; its permission lists can be upper bounds over argument-dependent paths [R10]. Store API level, native/Java boundary, caller identity, arguments, policy context and evidence separately. An obsolete map can still be correct for its old version.

2. **[SYSTEM → RESULT recommendation] Source/sink tags are not complete transfer semantics.** SuSi tells an analysis where flows may begin/end; StubDroid models internal API propagation [R08, R13]. Use both layers. Unknown methods, aliases, callbacks, native effects and ICC must conservatively propagate uncertainty, rather than silently preserving all labels.

3. **[SYSTEM → RESULT recommendation] Explicit taint is weaker than noninterference.** TaintDroid excludes implicit flow [R14]. D9-PROV includes PC dependencies; CNI/INI/TNI/PNI quantify over programs or multiple executions. A runtime trace with no flagged flow is not evidence for all of those properties [R36].

4. **[CLAIMED → RESULT recommendation] Secure single-agent designs need a multi-agent protocol.** The 2026 multiCaMeL paper describes attacks when downstream agents treat upstream untrusted output as privileged instructions [R39]. Its evaluation was not rerun, and current implementation release/license was not verified. Preserve separate authenticated instruction authority and data-origin labels across every agent boundary; do not erase taint at a convenient interface.

5. **[SYSTEM → RESULT recommendation] Hints and signatures do not prove effect truth.** MCP warns about untrusted annotations; SEP-3140 proposes authenticating declarations, not verifying the publisher's behavior [R32, R35]. Bind an attestation to code/version/configuration and independently justify its semantic claims. A signature is distinct from current owner approval, authority, or freshness.

6. **[RESULT — input-derived recommendation] Keep state and history distinct.** D9-LOCAL concerns current copies; NOEGRESS concerns a historical event. Erasing a remote copy cannot make “never left” true. Encrypting an envelope does not erase its historical origin. Endorsement/declassification changes trust/release permissions, not the authenticated origin DAG.

7. **[SYSTEM → RESULT recommendation] A modeled graph needs a sound abstraction and join rule.** Abstract interpretation already supplies this framework [R36]. Use union for possible origins/effects, intersection for guarantees across alternative branches, and fixpoints for unbounded loops. A bound on unrolling is a bound on explored executions unless a separate argument justifies completeness.

8. **[RESULT — input-derived recommendation] Concurrency makes several D9 contracts stronger than ordinary API calls.** Bind check and commit to the same policy epoch, authority, destination, descriptor and bytes. REVOKE needs a shared protected epoch covering aliases; FRESH needs atomic acceptance history; AUDIT needs atomic event/log commitment. A preflight result can become stale before commit.

9. **[SYSTEM → RESULT recommendation] Model-level success is conditional on the adapter.** Guardians, TACIT, CaMeLoT and Frama-C all depend on tool/library/host assumptions [R01–R03, R06]. Track two proof obligations: the implementation refines its summary, and composed summaries imply the policy. A verified second obligation does not discharge the first.

10. **[RESULT — assessment] Preserve honest uncertainty in the output.** The checker should distinguish “proved under assumptions,” “possible violation,” “unknown binding,” and “outside the model.” An invariant not proved to survive is not necessarily broken. A survived label is not a proved hyperproperty without its required relational semantics.

**[FOLKLORE — rejected]** “No network permission means no egress”; “encrypted data has no sensitive origin”; “signed metadata is true”; “MCP read-only hints are enforced”; “a new source commit establishes Android 16 coverage”; and “type-safe effect handlers imply complete security-effect tracking.” The primary sources and the supplied carrier definitions do not support those inferences.

**[RESULT — adoption decision]** Reuse existing effect/contract and policy machinery. Concentrate new engineering on **version-pinned adapter conformance, closed-world event coverage, joint operands, and sound composition across carriers**. The attachment does not yet justify making D9 a binding to one entire prior system: none was verified to meet its full scope. A hybrid binding to existing summary/checking infrastructure is justified; a claim of independent architectural novelty is not.
